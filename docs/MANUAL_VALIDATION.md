# 実機確認手順

この文書はユーザー環境での確認手順です。確認した範囲と結果は、関連するIssue・PRに記録してください。
まず小さな確認用ディレクトリで、herdrとCodexのバージョンを記録してください。

## モデル設定の確認

1. READMEの`models`コマンドで設定ファイルとマージ後の値を確認する。設定なしでは
   Worker=`gpt-6-luna / max / fast`、Design=`gpt-6.1-sol / max`、
   Reviewer=`gpt-6.1-sol / high`、Advisor=`gpt-6-astra / xhigh`となる。
2. ユーザー標準パス、`VISIBLE_TEAM_MODEL_CONFIG`、`--model-config`で一部の役割だけを
   上書きし、未指定項目は既定値が残ることを確認する。`models`だけではペインを作成しない。
3. 同じ設定で担当を起動し、`task.json`の`model`・`effort`・`service_tier`・
   `model_config_path`・`requested_codex_args`と、実セッション記録をそれぞれ確認する。
   起動引数だけで実モデル・実際のFast適用を確認できたと扱わない。
4. `spawn --model ... --effort ... --service-tier ...`が該当担当の設定だけを上書きし、
   権限は固定の`workspace-write / never`のままであることを確認する。
5. `service_tier: null`・`--service-tier inherit`ではプラグインからtier指定が付かないこと、
   不正な設定はペイン作成前にエラーとなることを確認する。
6. 設定ファイルを変更した後も、既存担当への`send`では以前のモデル・推論強度を保ち、
   新しい`spawn`から変更が反映されることを確認する。

## 0. 共有app-serverでの会話・画面登録

実行側に`CODEX_THREAD_ID`があり、`HERDR_*`がない状態で確認します。
`herdr pane list`で候補を取得し、会話IDや端末内容を照合してから、READMEの
`init --main-pane … --main-terminal-id … --socket …`を実行してください。

確認すること：

- `doctor --run`が成功し、実行記録にMainの会話IDと元の端末IDが入ること。
- 別の会話ID、会話IDの欠落・矛盾、誤った端末IDでは操作前に拒否されること。
- 他の画面へフォーカスを移しても、登録したMainを対象にすること。
- 子の報告で、役割・報告先・子自身の画面情報がツール実行環境へ届くこと。
- ユーザー設定や他セッションの環境が変更されないこと。

模擬テストでの成功と、実ペイン・実際のsandboxでの成功は区別します。

## 1. 導入と1担当

READMEの手順でインストールし、herdr内の新しいCodexで依頼します。

```text
$visible-team:visible-team
このリポジトリの構成をLuna 1担当に読み取り専用で調査させてください。
結果を回収し、担当ペインを閉じ、Mainで要点を報告してください。
```

確認すること：Mainの右に担当ペインが現れ、入力フォーカスを奪わず、
実際にLunaが動くこと。レビューや追加作業のない調査結果をMainが受理した後、
担当ペインだけが閉じること。
起動したCodexの表示やセッション記録から、モデルとeffortも確認してください。

## 2. 並列実行

```text
$visible-team:visible-team
実装の構成とドキュメントの構成を、独立したLuna 2担当に読み取り専用で
同時に調査させてください。各担当の報告を回収したら、そのペインを閉じてください。
```

確認すること：両方が同時に動き、作業名で識別でき、報告が混ざらないこと。
これは確認用の2担当であり、製品の並列数上限ではありません。
右側の境界を手で調整し、後の操作で配置全体が初期化されないことも確認します。

## 3. WorkerとReviewerの継続

```text
$visible-team:visible-team
確認用の小さな変更をLunaに実装させ、Solに独立レビューさせてください。
初回報告を回収した後もWorkerとReviewerを保持し、採用した指摘を元のWorkerに
修正させ、同じReviewerで再確認してください。レビュー全体を終える時点で両方を閉じてください。
```

既知の受け入れ条件と、その条件を満たさない場合を確認できる小さな候補を使います。
修正すべき指摘が出なければ、再依頼と修正の往復は未検証として記録します。

確認すること：

- 実装報告の回収後からレビュー待ちの間もWorkerが残り、修正依頼は元の会話・端末へ届くこと。
- Mainが指摘の採否と修正範囲を判断し、WorkerとReviewerにその判断が伝わること。
- 修正報告の回収後もWorkerが残り、再レビューも元のReviewer会話・端末で行われること。
- Reviewerはプロジェクトを変更せず、割り当てられた報告先だけを使うこと。
- 回収済みの完了報告と担当状態に変化がない保持中のペインは`wait`の未完了件数に入らず、
  新たな`send`後にはその依頼が待機対象に戻ること。保持だけを理由にMainが定期確認しないこと。
- Mainがレビュー全体の終了を判断してから、未完了作業のないWorker・Reviewerを閉じること。
  Advisorが同席している場合、Mainの作業全体が続く間は残ること。

## 4. 直接介入

担当が調査している間に、そのペインへ「この観点も含めてください」と直接入力します。

確認すること：担当が古い報告を無効化してから追加作業を行い、追加指示とその影響を
報告へ含めること。Mainが追加作業中の担当を閉じないこと。
報告回収後から終了直前の入力には競合する余地があり、完全な同期は保証していません。
問題が起きた場合は、後述の報告ファイルと操作順を残してください。

## 5. 子の固定権限・ブロックと配送失敗

Mainを普段使うAuto・Auto-reviewなどに切り替え、それぞれ新しい担当を起動します。
起動したCodexの`/status`等の表示と`task.json`の`requested_codex_args` / `launched_argv`を
確認し、全役割が`workspace-write + never`になり、Mainの設定は維持されることを確認します。
引数の記録だけで実際の適用を確認したことにはしません。

担当の`--cwd`に指定した確認用プロジェクトまたはworktreeで、小さなファイルの作成・編集と
報告の発行ができることを確認します。Reviewerはプロジェクトへ変更を加えず、報告先のみを使います。

次に、書き込み許可の対象外にある確認専用ディレクトリを用意し、そこへの小さなファイルの
新規作成を担当へ依頼します。既存データや設定ファイルは対象にしません。
期待する結果は、承認を求めずに操作が拒否され、操作内容・対象・エラー・理由・完了済みの作業を
含む`blocked`報告がMainへ返ることです。許可済みの場所を使ってしまった場合はこの確認にはなりません。

Mainが報告を回収してもペインが残り、自分の権限・承認ルールで対応した後に、`send`で
同じ担当が作業を再開できることを確認します。子の権限変更や広い権限での再起動は行いません。
ネットワークを禁止した確認環境では、取得が必要な依存関係についても同じ報告になることを確認できます。

サインインなど別の入力待ちが現れた場合も、ペインを残して状況を確認し、自動入力しないこと。
起動・指示送信がタイムアウトした場合、同じ仕事の二重起動・自動再送をしないこと。

## 6. 手動操作と対象の保護

Mainの隣に、ユーザー自身のシェルまたはエディタを置いてから担当を起動します。
担当ペインを移動したり、手動で閉じたりして、Mainへ状況を伝えます。

確認すること：ユーザー自身のペインやMainを閉じず、移動後も同じ端末を識別すること。
対象が失われた場合に、別のペインを代わりに閉じないこと。

## 7. 待機と重複通知

10〜30分程度かかる独立した作業を2担当へ依頼し、Mainの実行記録を確認します。
この確認では、Mainを起動する前に`background_terminal_max_timeout=3600000`を設定します。
推奨例は`codex -c background_terminal_max_timeout=3600000`です。この設定は実行ツールの
技術的な上限であり、結果待ちへ渡す`yield_time_ms`は変更しないため、両方の設定が必要です。
`wait --until-event`を1回だけ開始し、同時に動くwaiterがrunごとに1つであることを確認します。
同じ実行`session_id`の結果待ちに`yield_time_ms=3600000`を使い、外側の実行ラッパーが
`cell_id`を返す場合も同じcellを継続します。どちらかが早くyieldしても、helperの終端JSONが
なければ新しいwaiterを開始しないことを確認します。

無変化の10〜30分について、次をすべて満たすことをセッション履歴とプロセス一覧で確認します。

- 同一runのwaiterは常に1個
- helper timeout、新しいhelper起動、Mainの`status`・`read`が0回
- 変化のない進捗メッセージが0回
- 内部のherdr照会間隔が2秒から最大10秒へバックオフする

初回起動の早いyieldと、完了・要対応・プロセス終了・ユーザーの追加指示による早い復帰は
定期確認と区別します。引数が3600000でも、ホストや外側ラッパーが短く切り詰めていれば
1時間待機の成功とは扱いません。内部のherdr照会とMainのLLMによるツール呼び出しも区別します。

同じrunへ意図的に2個目のwaitを開始し、即座に`reason: waiter_already_active`と既存の
`wait_id`・PIDが返ること、最初のwaiterが継続することを確認します。通常の`--timeout 55`が
拒否されることも確認します。短時間timeoutを確認する単体テストだけが非公開のテスト用スイッチを使います。

1時間待機に非対応の環境では、Mainが具体的な制約を一度報告し、短いポーリングへ
自動で切り替えず、既存の待機・担当を保持することを確認します。

上位の運用指針により長い待機を避ける判断をした場合は、実行ツールの技術的なクランプや
上限を観測した場合と混同せず、判断理由と実測結果を分けて記録します。外側ラッパーの
1時間対応や実際の1時間待機を確認していない場合は未検証と記載します。

片方が`blocked`を報告したらMainで回収し、未解決事項を保持したまま他方を待ちます。
同じブロック通知が即座に繰り返されず、他方の完了や新しい報告は返ることを確認します。
1時間未満で通知を受け取った場合も、残り時間を待たずにMainが対応することを確認します。
続いて同じ担当へ`send`で再依頼し、新しい依頼の通知は抑制されないことを確認します。
報告なしの入力待ちでも、初回だけ通知され、状態が変われば再通知されることを確認します。

イベントでは`reason: event`、全担当の回収後は`reason: no_pending`が返ることを確認します。
`no_pending`で待機を再起動しないこと、ユーザーが途中で
Mainへ指示した際に応答できることを確認します。短いtimeoutの確認には、手動指定ではなく
単体テストの模擬時刻を使います。実運用で安全timeoutを
確認する場合は3600秒以上を指定し、`reason: safety_timeout`を1回だけ処理します。

herdrを模擬した回帰テストは`python3 -m unittest discover -s tests -v`で実行できます。
これはMainの実際の呼び出し間隔や、herdr上の画面・稼働を確認するものではありません。
Mainの実セッションは、対象rollout JSONLだけを指定して次のコマンドで集計します。

```bash
python3 plugins/visible-team/skills/visible-team/scripts/audit_wait_history.py \
  /path/to/main-rollout.jsonl
```

`waits`、`reasons`、`status_calls`、`read_calls`、`max_concurrent_waits`を上記の条件と照合します。

## 8. Astra XHIGH Advisor

Mainが重要なユーザー発言、合意・制約、相談論点、コードや失敗結果の抜粋をまとめ、
`spawn --role advisor`で起動します。難しいPlan作成と短い判断相談の両方で、
要求した引数と実際のセッション記録が`gpt-6-astra / xhigh`であることを確認します。
AdvisorにはFastの上書きを追加しません。herdrに見えるペインとCodexの会話を照合し、
実効権限とプロジェクトの未変更も確認します。

情報不足がある計画相談を使い、`blocked`報告を回収してペインが残ること、追加証拠を
`send`すると同じ会話・端末で改訂案が返ることを確認します。Mainの仮説がユーザー合意に
化けていないこと、古い方針を新しい指示に合わせて修正することも見ます。
個別相談を解決して現在の完了報告を回収した後もAdvisorを残し、同じ一連の作業に関する
別の判断相談を`send`で送ります。元の会話・端末が再利用され、新しい事実・変更した前提・
Mainの採否判断を踏まえた助言が返ることを確認します。独立レビューには別のSol Reviewerを使います。

Mainが途中報告を返す場合、ユーザーの返答を待つ場合、コンテキスト圧縮を挟んで再開する
場合にもAdvisorを保持し、taskパスを引き継いで同じ会話へ再相談することを確認します。
Mainが作業全体を終える後片付けの時点で、最新の完了報告を回収したAdvisorを閉じます。
未解決の`blocked`や回収後の活動がある場合は終了確認を回避せず、内容を確認して対応します。
無関係な作業への大きな移行などで会話を切り替える場合は、その理由と引き継いだ情報を記録します。

自動テストは`spawn`引数、役割指示、blocked→collect→send→complete→collect→close、
古い報告の拒否、別Mainからの追加指示拒否、Advisor自身のチーム操作拒否を模擬確認します。
実際のAstra推論、herdrの画面・指示送信、長時間待機を実証するものではありません。

品質・消費量は、現行構成、必要時相談、Astraによる初期Plan、Astra Main＋同じWorker構成を
同じ代表タスクで比較します。要求逸脱、重大な問題、手戻り、時間、Mainを含む総消費量を記録し、
会話＋証拠での欠落が疑われる事例だけ全履歴や要約中心とも比較します。
全履歴は評価用の対照であり、通常運用の転送方針にはしません。

## 問題を報告するとき

次の情報があると原因を追いやすくなります。

- herdr / Codex / Pythonのバージョン、OS
- 依頼内容、期待した動作、実際の動作、操作順
- Mainが受け取った`run` / `task`の場所と、補助スクリプトのエラー
- 必要な範囲の`task.json`、現在の`*.task.md`、`*.result.json`、`collected.json`、`wait-notices.json`
- 問題が見える画面

これらにはプロジェクト情報や入力した指示が含まれるため、共有する範囲を選んでください。
